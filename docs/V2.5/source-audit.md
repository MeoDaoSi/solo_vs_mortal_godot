## Executive findings

The project contains a Godot C# entrypoint with a useful Core/Data/Simulation/Application/Presentation shape, but its authoritative runtime is an older V1/V2 ruleset. The main scene is `scenes/Arena.tscn`, which uses `src/Presentation/Arena.cs`; it loads `data/configs/*.json` through `src/Data/Definitions/GameDefinitions.cs` and starts `src/Simulation/GameSession.cs`.

The largest gaps are the V2.5 state model and transaction boundaries: fixed 60 Hz simulation, typed lowercase content IDs, player Spirit/dodge/combat state, Density/pending/proof Soul progression, per-species Sync awards, banner gates, ally vitality and possession snapshots, equipment/skills/quests, encounter reward budgets, status/shield damage, and a WAL-backed save adapter. Existing implementation also exposes explicitly removed mechanics (Soul devouring, Essence, Bloodline, Crafting, pills, and old nature capabilities) through both C# APIs and visible UI.

The engine/language baseline differs. `solo_vs_mortal_godot.csproj` targets `Godot.NET.Sdk/4.7.2`, `net8.0`, and `project.godot` advertises Godot `4.7`, C#, Forward Plus; `export_presets.cfg` selects `gl_compatibility` for exports. The canonical README asks for Godot 4.5.2 Compatibility and the original implementation prompt asked for typed GDScript. The bounded decision is to reuse the existing typed C# architecture rather than rewrite it blindly: keep engine calls behind the existing Presentation boundary, avoid 4.7-only APIs, and verify/export with a 4.5.2 Compatibility installation before calling that baseline verified. Current audit evidence only confirms the installed 4.7.2 toolchain; 4.5.2 was not verified.

**Engine-baseline supersession (2026-09-10):** The preceding paragraph and later baseline observations are preserved as historical audit evidence. The user has since established Godot .NET 4.7.2 as the official V2.5 implementation baseline. A successful 4.7.2 compile/export is valid technical evidence, not gameplay acceptance. The Forward Plus editor feature versus `gl_compatibility` export-preset difference remains recorded and was not changed by this decision.

## Part 2 implementation status

The canonical foundation now exists in src/Data/Definitions/V25/CanonicalV25Definitions.cs. CanonicalV25Loader.LoadFromDirectory validates the pinned revision and content/balance versions before parsing, recomputes SHA-256 hashes from the physical files, rejects unknown nested fields, validates canonical lowercase DefinitionId/AssetId values, preserves PascalCase capability IDs, and cross-checks profile, species, region, skill, sync, quest, encounter, and asset references. It exposes a typed CanonicalContentRegistry and beta profile projections (beta_01 has two regions and five species). GameApplication.CreateFromDefinitionsDirectory is the shared bootstrap used by both Main and Arena, and the Windows export script now requires the five physical data/v2.5 files so a System.IO loader can resolve them outside the PCK.

The V2.5 save namespace is separate from legacy GameSaveCodec.CurrentVersion == 6. src/Application/Persistence/V25/V25SaveData.cs defines the schema-1 envelope, resource micro-units, Density proof/award records, Sync ledgers, receipts, payload checksum, strict unknown-field rejection, and range/uniqueness validation. src/Application/Persistence/V25/V25SaveStore.cs stages a validated temp file, writes a durable staged/committed WAL, promotes atomically while retaining .previous and .backup, detects idempotent transaction retries, and returns RejectedPreserved for invalid recovery input. Explicit manual restore preserves the replaced current file as .rejected. This is a save foundation; full combat suspension and live V2.5 state capture are still pending.

src/Application/Persistence/LegacySaveAdapter.cs recognizes legacy versions 1–6 as their own namespace and rejects unsupported/future versions while preserving the original. It performs exact legacy-runtime identity, numeric, reference, banner, possession, runtime, inventory, point, and world checks before GameApplication.RestoreSave mutates state. In canonical mode, a recognized legacy v1–v6 payload is explicitly rejected before mutation because the missing Soul/Density/Sync mapping is not lossless. GameSaveCodec now rejects malformed present fields instead of silently skipping them. Legacy records are never converted into synthetic V2.5 Density, Sync, milestone, or receipt data.

GodotSaveStore now uses the durable physical-file primitive for legacy runtime saves, and Arena blocks autosave and _ExitTree writes after any load or restore failure. A valid load clears the block; missing files leave the new game untouched. This closes the corruption-overwrite path while the runtime still writes the legacy v6 path. The installed Godot command is 4.7.2 stable; the canonical Godot 4.5.2 Compatibility baseline remains unverified.

The former tests/ tree and src/Presentation/PerformanceSoak.cs probe were removed under the explicit user cleanup instruction, and their project/export references were removed. The user remains the sole gameplay tester; build and launch smoke checks do not claim the 18 manual acceptance cases. Obsolete gameplay docs are marked historical and docs/README.md is the source checkout's single gameplay-document index. Old configs, obsolete gameplay APIs, and broad art roots remain until later implementation parts migrate their dependencies.

The current manual review boundary is therefore: (1) launch scenes/Arena.tscn, (2) inspect canonical bootstrap failure behavior by changing a pinned file or hash and restoring it, (3) exercise legacy save rejection/recovery through the real UI, and (4) review the 18 gameplay cases after their corresponding systems are implemented. No reference-vector or automated test result is implied by this status.

Repair update: the live combat boundary now cancels dead actor casts/projectiles, clears projectile state on player death, rejects stale cast snapshots after same-pass boss stagger, and only lets ActorAI use self buffs with a hostile target (signature heal remains strict HP<70%). WAL recovery matches SaveId, TransactionId, sequence, and envelope checksum, preserves malformed WALs while selecting valid candidates, and appends history after recovered commits. Restore prevalidation covers actor AI/source identity, exact cast phase/timing, projectile lifetime/offense snapshots, and knockback bounds before any state swap.
